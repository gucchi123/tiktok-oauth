<p>I run close to twenty automated content pipelines as a side project. Generation, formatting, scheduling, publishing. Over the past few months I have made the same class of mistake three times, and each time I thought I had already fixed it.</p>
<p>Here is the progression:</p>
<ol><li>I duplicated a rule across scripts — and one copy silently overwrote the other&#x27;s work.</li><li>I centralized the rule into one module — but code paths existed that never called it.</li><li>I wired the gate into every path — and then the gate logic itself rejected things it should have allowed.</li></ol>
<p>Most engineering advice stops at step one. &quot;Don&#x27;t repeat yourself, extract it into a shared module.&quot; That advice is correct and it is not enough. Step two is where I actually lost time, and step three is where I nearly did real damage.</p>
<p>Keeping this generalized — no product names, no platform specifics. The shape of the problem is what matters.</p>
<h2>Round one: two copies of a rule, quietly fighting each other</h2>
<p>Outgoing posts had to carry a compliance marker. A short required string at the top of the body. Simple enough that I wrote the check inline in each publishing script.</p>
<p>Then one day I standardized the marker&#x27;s format. I updated the templates. A few hours later the old format was back in the live output.</p>
<p>The reason was mundane. One script checked for the old string, did not recognize the new one as a valid marker, and helpfully re-injected its own. The template was correct. The runtime kept undoing it. Reading the template told me nothing — I had to look at what actually got published.</p>
<p>The fix was the obvious one: move the check and the formatting into a single module, and make it accept both the old and new forms so nothing regresses during the transition.</p>
<p>One detail turned out to matter more than the centralization itself. I made the function return what it changed, not just the changed text:</p>
<pre>def normalize(text):<br>&nbsp;&nbsp;&nbsp;&nbsp;actions = {}<br>&nbsp;&nbsp;&nbsp;&nbsp;out = text<br>&nbsp;&nbsp;&nbsp;&nbsp;if needs_marker(out) and not has_marker(out):<br>&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;out = MARKER + out.lstrip()<br>&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;actions[&quot;marker_injected&quot;] = True<br>&nbsp;&nbsp;&nbsp;&nbsp;return out, actions</pre>
<p>If a function silently rewrites your content, then the next time you hit a design flaw you have no way to reconstruct what happened. Returning an action log costs nothing and the caller can put it straight into the logs.</p>
<h2>Round two: the gate existed, and almost nothing called it</h2>
<p>This is where I got comfortable, and comfortable was the mistake.</p>
<p>I had placed the normalization &quot;right before publishing.&quot; That phrase was doing a lot of unearned work. There was not one publishing path. When I actually counted them on a later project, the tally looked like this:</p>
<p><strong>Path / Routes through the gate</strong></p>
<ul><li>CLI tool — yes</li><li>Daily generation job — no — called the endpoint directly</li><li>Weekly feature job — no</li><li>Backfill / enrichment batch — no</li><li>...seven more — no</li></ul>
<p><strong>One path out of eleven.</strong> I had added the gate to the CLI, watched it work, and marked the task done.</p>
<h3>Enumerate the paths mechanically, and distrust the first pass</h3>
<p>&quot;That&#x27;s probably all of them&quot; is not a methodology. I enumerated by searching for the thing that actually creates content — the create call itself, excluding updates:</p>
<pre>grep -rn &#x27;POST&quot;, &quot;posts&quot;\|/posts&quot;&#x27; --include=*.py .</pre>
<p>That found seven. Four more surfaced later, because they built the request slightly differently. The lesson is not &quot;use grep.&quot; It is: <strong>do not assume one search pattern found everything.</strong> Search by the effect you care about, then search again by a different signature.</p>
<h3>Test the wiring, separately from the logic</h3>
<p>This is the part that actually stopped the bleeding, and it is the part I had never written before.</p>
<p>Testing that a validation function returns the right answer is normal. Testing that every entry point <em>calls</em> it is a different assertion, and it runs against the source, not the behavior:</p>
<pre>PUBLISH_PATHS = [&quot;cli.py&quot;, &quot;daily.py&quot;, &quot;weekly.py&quot;, &quot;enrich.py&quot;, ...]<br><br>for name in PUBLISH_PATHS:<br>&nbsp;&nbsp;&nbsp;&nbsp;src = (HERE / name).read_text(encoding=&quot;utf-8&quot;)<br>&nbsp;&nbsp;&nbsp;&nbsp;assert &quot;assert_publishable&quot; in src, f&quot;{name} does not call the gate&quot;<br><br>&nbsp;&nbsp;&nbsp;&nbsp;# no local copies of the threshold<br>&nbsp;&nbsp;&nbsp;&nbsp;own = re.search(r&quot;^(?!from _gate).*MIN_CHARS\s*=\s*\d+&quot;, src, re.M)<br>&nbsp;&nbsp;&nbsp;&nbsp;assert own is None, f&quot;{name} defines its own threshold&quot;</pre>
<p>Two properties, verified independently: <em>the logic is right</em>, and <em>everything goes through it</em>. Once I separated those, this class of incident stopped.</p>
<p>Paths I deliberately excluded got a comment explaining why. Without it, every future audit re-flags them as gaps and someone re-investigates:</p>
<pre># Intentionally out of scope:<br>#   _oneoff.py  : already-executed single-use script, never re-run<br>#   builder.py  : body goes in via the CLI, so it is already covered<br>#   (plugin)    : runs inside the host application, never touches our code</pre>
<p>That last one is worth dwelling on. Some paths genuinely cannot be gated because they never execute your code at all. Writing that down is more honest than pretending coverage is complete.</p>
<h2>Round three: the gate was wired everywhere, and it was wrong</h2>
<p>With eleven paths routed through one chokepoint, a bug in that chokepoint is no longer a local defect. It is a single point of failure with full reach.</p>
<p>The goal was to refuse to publish anything too short. The complication: every post ends with a boilerplate block, and boilerplate is long enough on its own to clear any reasonable minimum. An empty post with boilerplate would pass.</p>
<p>So I measured the body only up to the boilerplate marker:</p>
<pre># broken<br>def visible_len(html):<br>&nbsp;&nbsp;&nbsp;&nbsp;cut = len(html)<br>&nbsp;&nbsp;&nbsp;&nbsp;for marker in (&quot;&lt;!-- CTA&quot;, &#x27;class=&quot;promo-block&quot;&#x27;):<br>&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;i = html.find(marker)<br>&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;if i != -1:<br>&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;cut = min(cut, i)     # truncate at the marker<br>&nbsp;&nbsp;&nbsp;&nbsp;body = re.sub(r&quot;&lt;[^&gt;]+&gt;&quot;, &quot; &quot;, html[:cut])<br>&nbsp;&nbsp;&nbsp;&nbsp;return len(re.sub(r&quot;\s+&quot;, &quot;&quot;, body))</pre>
<p>Two bugs in six lines.</p>
<p><strong>It cut in the middle of a tag.</strong> One of those markers is an attribute <em>inside</em> a div, so truncating at its offset leaves a fragment like <code>&lt;div class=&quot;promo-b</code> with no closing bracket. The tag-stripping regex requires a <code>&gt;</code>, so it does not match the fragment, and the raw attribute text gets counted as body content. The measurement was inflated by the very markup it was trying to exclude.</p>
<p><strong>It discarded everything after the block.</strong> This one was worse. New posts append boilerplate at the end, so truncation looks harmless. Older posts had boilerplate embedded <em>mid-article</em>. A post with 1,205 characters of real content measured as far less, because everything past the block was thrown away.</p>
<p>The gate was correctly wired into all eleven paths. It was about to correctly, consistently, and universally block legitimate content.</p>
<p>The fix is conceptually small: <strong>remove the block, don&#x27;t truncate at it.</strong></p>
<pre>_PAIRED = (&quot;CTA&quot;, &quot;FAQ&quot;, &quot;LINKS&quot;)          # wrapped in open/close comments<br>_DIV_MARKERS = (&#x27;class=&quot;promo-block&quot;&#x27;,)     # a single div, no closing comment<br><br>def strip_boilerplate(html):<br>&nbsp;&nbsp;&nbsp;&nbsp;body = html or &quot;&quot;<br>&nbsp;&nbsp;&nbsp;&nbsp;for name in _PAIRED:<br>&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;body = re.sub(rf&quot;&lt;!--\s*{name}[^&gt;]*--&gt;.*?&lt;!--\s*/{name}\s*--&gt;&quot;, &quot; &quot;,<br>&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;body, flags=re.S | re.I)<br>&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;# fallback for data where the closing comment was lost<br>&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;body = re.sub(rf&quot;&lt;!--\s*{name}[^&gt;]*--&gt;.*\Z&quot;, &quot; &quot;, body, flags=re.S | re.I)<br>&nbsp;&nbsp;&nbsp;&nbsp;for marker in _DIV_MARKERS:<br>&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;body = strip_div_block(body, marker)<br>&nbsp;&nbsp;&nbsp;&nbsp;return body</pre>
<p>For the div case, a non-greedy match finds the wrong closing tag as soon as anything nests. You have to walk forward counting opens and closes until the depth returns to zero. It is more code than a regex and it is the only version that survives real documents.</p>
<h2>Write the test that catches a false positive</h2>
<p>I found the truncation bug through a regression test — but not the first one I wrote. My original test only checked that short content gets blocked:</p>
<pre>assert blocked(&quot;&lt;p&gt;too short&lt;/p&gt;&quot;)<br>assert not blocked(&quot;&lt;p&gt;&quot; + &quot;x&quot; * 1500 + &quot;&lt;/p&gt;&quot;)</pre>
<p>Both passed. The bug sat right underneath. What exposed it was constructing the shape that actually occurs in production — real content on <em>both</em> sides of the boilerplate:</p>
<pre>mid = &quot;&lt;p&gt;&quot; + &quot;x&quot;*700 + &quot;&lt;/p&gt;&quot; + BOILERPLATE + &quot;&lt;p&gt;&quot; + &quot;y&quot;*700 + &quot;&lt;/p&gt;&quot;<br>assert visible_len(mid) == 1400, &quot;content after the block must count&quot;<br>assert not blocked(mid), &quot;must not block legitimate content&quot;</pre>
<p>For anything gate-shaped, the &quot;must not reject valid input&quot; tests are the ones that go missing. The rejection cases are vivid — you just built the thing that rejects, so you can picture what it should catch. The acceptance cases feel too obvious to write down. That asymmetry is exactly where the false positives hide.</p>
<h2>Measure the distribution before you pick a threshold</h2>
<p>One last thing, because guessing a minimum is how you halt an entire pipeline on day one.</p>
<p>Before setting the number, I wrote a throwaway tool that measured what the existing content actually looks like, with boilerplate excluded:</p>
<pre>=== siteA, last 30 posts (boilerplate excluded) ===<br>&nbsp;&nbsp;min 1497 / median 2337 / max 11563<br>&nbsp;&nbsp;threshold 1200 -&gt; would block: 0 posts (0%)<br><br>=== siteB, last 30 posts ===<br>&nbsp;&nbsp;min 147 / median 2161<br>&nbsp;&nbsp;threshold 1200 -&gt; would block: 4 posts (13%)<br>&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;147  post-slug-one<br>&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;160  post-slug-two</pre>
<p>siteB&#x27;s outliers turned out to be genuinely broken records worth blocking. I only knew that because I looked. And I encoded the constraint in the test suite so a future me cannot quietly raise the threshold past the observed floor:</p>
<pre>assert MIN_CHARS &lt; 1866, &quot;threshold must stay below the measured minimum&quot;</pre>
<h2>What I actually take away from this</h2>
<ul><li>Centralizing a rule is the <strong>starting point</strong>, not the finish line.</li><li>Verify <strong>that every path calls the gate</strong> as a separate assertion from whether the gate&#x27;s logic is right. Enumerate paths mechanically, and record intentional exclusions in code.</li><li>Test that the gate <strong>lets valid input through</strong>, not only that it stops invalid input. The second kind of test is the one you forget.</li><li>Never pick a threshold by intuition. Measure the distribution of real data first.</li></ul>
<p>All three incidents had the same root cause, and it was not &quot;insufficient abstraction.&quot; It was that the scope I <em>believed</em> I had covered was narrower than the scope I had actually covered. The durable fix was not a better module. It was moving the definition of &quot;covered&quot; out of my memory and into a test.</p>
